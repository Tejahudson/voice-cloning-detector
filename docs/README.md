# VoiceGuard-AI — Real vs. Cloned Voice Detector (Prototype)

Prototype built for **SIH26104 — "AI-Powered Real-Time Detection and Prevention of Voice Cloning Impersonation Attacks"** (Team Victrix). See `../SIH26104_Victrix_VoiceGuardAI.pdf` for the original idea submission this prototype demonstrates.

This is a **working demo**, not the production system described in the deck: it analyzes uploaded audio files (rather than a live phone call) using genuine signal-processing forensics, streamed to the UI to feel real-time.

## Quick start

### Backend (FastAPI)

```bash
cd backend
python -m venv venv
./venv/Scripts/activate        # Windows
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

The API listens on `http://127.0.0.1:8000`. A SQLite file `backend/voiceguard.db` is created automatically on first run (users + analysis history only — never raw audio).

**First run downloads the detection model** (~1.2 GB, cached in `~/.cache/huggingface`). The server starts immediately and warms the model in the background; `GET /api/health` reports `detector_ready` so you can tell when it's loaded (~20s from cache after a restart). Analysis falls back to the heuristic scorer if the model can't load.

### Frontend (React + Vite)

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The dev server proxies `/api` and `/ws` to the backend on port 8000 (see `frontend/vite.config.ts`), so no CORS configuration is needed in development.

### Try it

1. Open the app and click **Open analyzer** — there are no accounts or sign-in.
2. On the **Analyze** page, either **upload files** or **record from your mic**:
   - *Upload file* — drop in a real recording and, separately, an AI-generated/cloned clip (from any TTS or voice-cloning tool). WAV is the most reliable format; MP3/M4A/FLAC/OGG also work if the host has an audio codec backend available.
   - *Record from mic* — click record, speak (or play a suspected cloned voice out loud), click stop, and it analyzes that take. The browser decodes and re-encodes the recording to 16 kHz mono WAV client-side, so no server-side ffmpeg is needed. Aim for 3+ seconds.
3. Watch the waveform, spectrogram, pitch contour and the live streaming risk score (updates roughly once a second per chunk, mirroring the PS26104 brief's real-time cadence).
4. Compare verdicts and risk scores across several real vs. cloned clips — this is the main way to sanity-check the heuristic on your own material.
5. Check **History** for a running log of every analysis on this instance (shared, since there are no accounts).

## How detection works

Detection runs in two layers.

### 1. Trained model — the actual verdict

`backend/app/services/trained_detector.py` runs **`garystafford/wav2vec2-deepfake-voice-detector`** (Apache-2.0), a Wav2Vec2-XLSR classifier fine-tuned specifically for synthetic-speech detection on human recordings plus clips generated by ElevenLabs, Amazon Polly, Kokoro, Hume AI, Speechify and Luvvoice. Labels are `{0: real, 1: fake}`; it expects 16 kHz mono.

Clips longer than 10s are scored in 10s windows (max 3) and averaged, since the model card reports best accuracy on 2.5–13s audio. Clips under 2.5s are flagged with a reliability warning in the UI. Inference is CPU-only and takes roughly 2–6s per clip.

The risk score, verdict and confidence shown in the UI all come from this model.

### 2. Heuristic features — explainability only

`feature_extraction.py` + `risk_scoring.py` compute real acoustic/spectral/prosody features with `librosa`/`numpy`/`scipy`. **These no longer decide the verdict** — they are displayed as supporting signal-level context:

| Feature | What it measures | Cloning signal |
|---|---|---|
| Pitch (F0) jitter | Cycle-to-cycle pitch instability | Unnaturally *low* jitter |
| Amplitude shimmer | Frame-to-frame loudness variation | Unnaturally *low* shimmer |
| Harmonics-to-noise ratio | Signal cleanliness vs. background/mic noise | Unnaturally *high* HNR |
| Spectral flatness / flux | How tonal and how fast the spectrum evolves | Over-smoothed flux |
| Zero-crossing rate variance | High-frequency/noise irregularity | Unnaturally *low* variance |
| MFCC delta variance | Frame-to-frame timbre dynamics | Unnaturally *low* variance |
| Formant bandwidth variance | Vocal-tract resonance stability | Unnaturally *low* variance |

**Why the heuristic was demoted.** Its thresholds were illustrative baselines from general speech-science literature, never fitted to labeled data — and in testing it was confidently *wrong*: on a synthetic TTS sample the trained model scored 99.4% fake while the heuristic scored it 1.5/100 ("real", 97% confidence). Modern voice cloning deliberately reproduces natural jitter, shimmer and even background noise, so "unnaturally smooth = synthetic" no longer holds. Its score is still computed and shown for transparency, labelled as secondary.

**Swapping detectors.** Both layers sit behind small interfaces called from `backend/app/routers/ws.py`: `trained_detector.predict(y, sr) -> TrainedResult` and `score_features(feats) -> RiskResult`. Point `settings.trained_model_name` at a different Hugging Face audio-classification checkpoint (or set `enable_trained_model=False` to run heuristic-only) without touching the API contract or the frontend.

## Privacy & operational posture

**There is no authentication.** Accounts, JWTs and password hashing were removed: the analyzer is open, and analysis history is a single shared list rather than per-user. Anyone who can reach the server can use it, so put it behind a reverse proxy or a private network before exposing it beyond localhost.

What the system still does:

- Uploaded audio bytes live only in an in-memory holding area (`app/services/pending_store.py`) between upload and the WebSocket analysis pass, then are discarded — never written to disk, never persisted to the database. Only the verdict summary (filename, score, verdict, confidence, top 4 feature contributions) reaches the history table.
- A sliding-window rate limiter caps `/analyze/upload`, keyed by client IP.
- Uploads are validated against a file-type allowlist and a 25 MB ceiling.
- Intended for HTTPS/WSS in any real deployment; the dev setup runs over plain HTTP/WS on localhost only.
